## Оптимизация и поддержка

- [Main](../src/pages/Main.tsx) загружает Ойнелово через отдельный lazy import.
  Прямые импорты секций исключают загрузку CSS неиспользуемых секций через barrel.
  Собственный chunk Main уменьшился примерно с 54 до 13 КБ JS и с 53 до 9 КБ CSS
  до gzip. Общие зависимости вынесены в отдельные chunks; это сравнение размера
  Main, а не обещание такого же сокращения общего трафика первой загрузки.
- `dist` исключён из Git. Локальная сборка остаётся доступна, workflow и команды
  deploy уже создают её из исходников. Это устраняет устаревшие bundles и
  изменения рабочего дерева после каждого build.
- Вместо `latest` заданы совместимые диапазоны текущих версий; lockfile сохраняет
  точные версии. Добавлена команда `npm run typecheck`.
- Удалён повторный экспорт форматтера телефона.

## Следующие задачи

Эти пункты обнаружены при аудите и остаются открытыми.

1. **P1 — ограничить попытки входа и отправку заявок.**
   `POST /api/admin/login` выполняет проверку пароля без ограничения частоты,
   `POST /api/contact` отправляет каждую валидную заявку в Telegram. Проверка
   Origin защищает браузерные запросы администратора, но не ограничивает
   произвольный HTTP-клиент. Нужна отдельная политика лимитов/антиспама и
   её конфигурация в production. Один из вариантов —
   [Cloudflare Rate Limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).
2. **P2 — защитить одновременное редактирование одного участка.**
   Две вкладки загружают старую строку; одна меняет цену, другая адрес.
   Более поздний полный PUT второй вкладки может вернуть прежнюю цену.
   Нужен серверный контроль версии и ответ 409 либо контракт обновления отдельных
   полей. Текущие `updated_at` имеют секундную точность, поэтому просто сравнить
   их недостаточно для надёжного счётчика версии.
3. **P2 — сохранять или блокировать черновики при переходе Back внутри SPA.**
   `beforeunload` не вызывается для всех клиентских переходов BrowserRouter.
   Нужен отдельный механизм навигации или сохранения черновиков; предупреждение
   при reload/закрытии документа этот сценарий не покрывает.
4. **P2 — закрепить браузерные проверки в CI и проверить транзакции на D1/SQLite.**
   Сейчас проверка D1 использует тестовую реализацию `batch`, которая проверяет
   валидацию до записи, но не моделирует rollback при ошибке SQL внутри batch.
   Новые UI-сценарии проверены в изолированном Chrome, а постоянные регрессии
   телефона и HTTP добавлены в Node suite.
5. **P3 — сократить объём публикуемых исходных ассетов и внешнего hero.**
   `public` содержит исходные TTF, PNG/reference и полный masterplan вместе
   с используемыми производными. Они копируются в build даже без обращений
   браузера. Исходники можно вынести из публикуемого каталога; для внешнего
   hero 1920 px добавить собственные адаптивные варианты.
6. **P3 — дополнить доступность таблицы и проверить контраст.**
   Горизонтальной области публичной таблицы полезен focusable region, как в
   Admin. Небольшие золотые ссылки и приглушённые подписи требуют проверки
   контраста на фактическом фоне. Не менялись дизайн и маркетинговые тексты.
7. **P3 — скрыть пароль в интерактивном CLI.**
   Генератор использует обычный readline, который показывает ввод в терминале.
   Проверка допустимой длины исправлена; маскированный ввод остаётся отдельным
   улучшением локального инструмента.
