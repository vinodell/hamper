# Размещение Хампер на Hostland

Этот документ сопровождает подготовленную миграцию с Cloudflare. Аккаунт и домен
на Hostland ещё не настроены; код и архив можно проверить до размещения. Действующая
база Cloudflare не изменяется автоматически, DNS и опубликованный сайт не переключаются.

## Что подготовлено

```text
Браузер в России
       │ HTTPS, один домен
       ▼
Hostland: статические страницы / изображения / шрифты
       │ /api
       ▼
Node.js API ──► SQLite: участки, настройки акции, заявки Journal
                    вне публичного каталога
                         │ сохранённая очередь уведомлений
                         ▼
                    Telegram Bot API
```

React и дизайн сохранены. Workers/D1 заменены обычным Node.js приложением и
файловой SQLite. Для небольшого каталога это не требует отдельного сервера базы,
сетевого соединения с БД и стороннего драйвера. Записи выполняются транзакционно;
WAL допускает чтение при сохранении, SQLite сериализует записи разных процессов.
Заявка считается принятой после успешного сохранения и показывается в `/admin/`.
В отдельной секции **Journal** всегда остаётся основная запись заявки. Telegram
дополнительно получает уведомление, если настроен бот; его недоступность не мешает
сохранению обращения и не требует повторной отправки формы пользователем.

Hostland документирует российское размещение, Node.js, SSH, HTTPS и настройку
приложения через панель: [хостинг](https://www.hostland.ru/hosting),
[установка Node.js](https://www.hostland.ru/ru/docs/manual/avtomaticheskaya-ustanovka-nodejs).
При выборе сервера нужен Node.js **22.13 или новее**, рекомендуется **24 LTS**.
Проверьте выбранную версию: проект использует встроенный `node:sqlite`, а не PHP.
Поддержка Node.js в тарифе сама по себе не подтверждает нужную установленную версию.

## 1. Подготовить архив на компьютере

Заполните публичные контакты в `.env.local` по `.env.example`. Эти значения
становятся частью клиентской сборки; пароль администратора и серверный секрет
в `VITE_*` не помещают.

```bash
npm ci
npm test
npm run build
npm run package:hostland
```

Для упаковки нужен установленный `zip`. Команда создаёт два архива и их
распакованные версии для ревью:

- `release/hamper-hostland_YYYY-MM-DD_HH-mm-ss_MSK.zip` и `release/hamper-hostland/` — полное приложение;
- `release/hamper-public-update_YYYY-MM-DD_HH-mm-ss_MSK.zip` и `release/hamper-public-update/` — обновление
  только клиентской части: `public/`, `UPDATE.md` и `release-manifest.json`.

Имена ZIP содержат дату и время упаковки по Москве (`Europe/Moscow`). Точные
имена свежих архивов указаны в `release/README.md`; время создания и SHA-256
обоих ZIP сохранены в `release/verification.json`. Распакованные каталоги
сохраняют фиксированные имена.

Оба используют одну клиентскую сборку. Полный архив содержит:

```text
server.js                    # вход Passenger
package.json                 # запуск без npm-зависимостей
build/server/                # собранный сервер
server/migrations/           # SQL-миграции
public/                      # единственный публичный каталог
private/                     # пустое место для локальной БД
tmp/                         # файл restart.txt создаётся при перезапуске
.env.server.example          # без действующих секретов
create-password-hash.mjs
INSTALL.md
release-manifest.json        # контрольные суммы файлов
```

Рабочая БД, резервные копии, `.env.server`, mock-данные, `node_modules` и исходные
DJI JPG/HEIC/DNG не упаковываются. Оптимизированные WebP включены. Архивы не
являются резервной копией данных. Упаковщик заново создаёт только собственные
каталоги и удаляет старые ZIP этих двух типов после успешного создания обоих
новых архивов. Выгрузки данных и `release/review/` сохраняются.

## 2. Создать приложение в панели Hostland

В панели откройте **«Сайты» → «Прикрепление домена | Создание сайта»**.
Для существующего домена нажмите **Nodejs**, затем **Добавить**. Для нового —
**«Прикрепить домен | Создать сайт»**, укажите домен и перейдите на вкладку **Nodejs**.
В **«Каталог приложения»** задайте, например, `hamper`. Размещайте приложение
в корне домена: поле **«URL приложения»** оставьте пустым, как описано Hostland.
Сохраните изменения и дождитесь завершения установки.

Документированные пути имеют вид:

```text
/home/hostXXXXXXX/example.ru/projects/hamper/server.js
/home/hostXXXXXXX/example.ru/projects/hamper/public/
/home/hostXXXXXXX/example.ru/projects/hamper/tmp/restart.txt
/home/hostXXXXXXX/example.ru/node/ВЕРСИЯ/bin/node
/home/hostXXXXXXX/passenger_log
```

Подставьте свои аккаунт, домен и каталог. Через SSH или терминал панели проверьте
`node -v` и `node -e "require('node:sqlite')"` выбранным интерпретатором. Если
автоустановка выбрала старую версию, сначала установите подходящую через доступные
настройки Hostland или поддержку. На сервере выбирают современный Node, а сборку
выполняют на компьютере/CI.

Загрузите **содержимое** архива в каталог приложения, чтобы `server.js` лежал
не во вложенной папке, а ровно по первому пути выше. Внешний document root
должен указывать на `public/`, не на весь каталог приложения. Исходники сервера,
секреты и база не должны находиться в `public/`.

## 3. Настроить сервер

На сервере в каталоге приложения скопируйте `.env.server.example` в `.env.server`.
Создайте хэш пароля командой `node create-password-hash.mjs` и вставьте результат
в `ADMIN_PASSWORD_HASH`. Сгенерируйте отдельный секрет:

```bash
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Пример настроек, все значения заменяются своими:

```dotenv
ADMIN_LOGIN=your-admin-login
ADMIN_PASSWORD_HASH=generated-salt-and-hash
SESSION_SECRET=generated-random-secret-at-least-32-characters
PUBLIC_ORIGIN=https://example.ru
PUBLIC_DIR=./public
DATABASE_PATH=/home/hostXXXXXXX/example.ru/private/hamper.sqlite
HOST=127.0.0.1
PORT=8787
```

`PUBLIC_ORIGIN` — точный HTTPS origin без `/hamper` и других путей. Если работает
вариант `www`, используйте один основной адрес и настройте перенаправление второго.
Файл БД лучше хранить в постоянном приватном каталоге **вне обновляемого приложения**;
доступ на запись нужен только владельцу приложения. Сам SQLite-файл получает
ограниченные права. Каталог должен находиться на локальном диске сервера, не на
сетевом/публичном хранилище. Не копируйте настройки Cloudflare в `.env.server`.

Passenger стартует `server.js`; сервер загружает `.env.server` из каталога
приложения независимо от текущей рабочей папки процесса. Переменные, заданные
окружением сервера, имеют приоритет. `PORT` нужен и для самостоятельного локального
запуска; Passenger управляет внешним подключением к приложению.

### Уведомления Telegram и Journal

Чтобы сохранить прежний канал заявок Telegram, добавьте в `.env.server`:

```dotenv
TELEGRAM_BOT_TOKEN=token-from-your-bot
TELEGRAM_CHAT_ID=your-chat-id
```

Можно использовать того же бота и чат, что были у Cloudflare: имена переменных
сохранены. Перенесите значения самостоятельно из своих защищённых настроек;
секреты не помещают в Git, `VITE_*`, frontend или публичный каталог. Пользователь
должен предварительно открыть диалог с ботом и нажать Start; для группы добавьте
бота в нужный чат и разрешите отправку сообщений. Подробнее:
[официальная инструкция Telegram](https://core.telegram.org/bots#how-do-i-create-a-bot).

Внутренний порядок: одна транзакция сохраняет заявку и задание Telegram, после
чего форма получает успех. Отправка выполняется фоновым обработчиком. Очередь
хранится в SQLite и переживает перезапуск; в Journal видны состояния «в очереди»,
«доставлено», «ошибка отправки» или «Telegram не настроен» и число попыток.
Если хотя бы один параметр пуст, заявка сохраняется только в Journal. Заявки,
полученные без настроенного бота, задним числом в Telegram не рассылаются.

При временных ошибках сервер делает до восьми попыток с увеличением паузы.
Ограничение `retry_after`, возвращённое Telegram, сохраняется в базе и действует
на всю очередь, включая новые заявки и другие процессы приложения. Запросы
имеют таймаут восемь секунд и не удерживают отправку формы; обработчик проверяет
очередь при запуске и каждые 15 секунд. Формат и ограничения метода:
[Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage),
[ResponseParameters](https://core.telegram.org/bots/api#responseparameters).
Автоматическая обработка требует работающего Node-процесса; при остановке
Passenger ожидающие задания продолжатся при следующем запуске приложения.
При обрыве соединения после фактической доставки, но до получения подтверждения
возможен повтор уведомления; номер заявки позволяет сопоставить его с Journal.

## 4. Создать схему и перенести данные

В каталоге приложения выполните выбранным Node:

```bash
node --env-file-if-exists=.env.server build/server/cli.js migrate
```

Миграции создают пустые таблицы и служебный журнал. Повторный запуск не выполняет
их повторно; изменение ранее применённого файла обнаруживается. Автоматического
заполнения тестовыми участками нет.

Для сохранения действующих цен, статусов, описаний и настроек сначала выгрузите
SQL существующей D1 средствами прежнего проекта/панели Cloudflare. Это разовая
операция чтения источника, не зависимость нового сайта. Поместите экспорт в
приватный каталог на Hostland, затем выполните:

```bash
node --env-file-if-exists=.env.server build/server/cli.js import-d1 /private/path/legacy-d1.sql
```

Поддерживается также JSON-объект `{ "plots": [...], "settings": { "promotion":
{ "enabled": false, "discountPercent": 10 } } }` с полями API или базы.
Импорт сохраняет базовую и полную цену, документы, кадастровый номер, Домклик,
описание, адрес и временные отметки. Старые записи с единицами `сот.` и `₽`
нормализуются. Некорректные данные отменяют весь импорт, а не часть строк.

Целевая база должна быть пустой: импорт не перезаписывает уже заполненные
участки, заявки и настройки. Временный SQL-разбор происходит в отдельной базе
в памяти; исполняемые команды источника не применяются к рабочему файлу.
Экспорт содержит данные вашего проекта: не храните его в `public/` и Git.

Если старых данных нет, подготовьте JSON с действительными участками и
настройками и импортируйте его той же командой. Для участков Ойнеловских далей
карта использует точные номера `1-01`…`1-21`. Фикстуры `mock/` в production
использовать не нужно.

## 5. HTTPS, запуск и проверка

Включите сертификат Hostland и HTTPS для основного домена. DNS должен указывать
на Hostland напрямую; Cloudflare proxy в обслуживании домена не нужен. Пока
проверяете подготовленное размещение, старый сайт и его БД можно оставить без
изменений. Переключение рабочего домена выполняется отдельным согласованным шагом.

Для перезапуска создайте/обновите файл `tmp/restart.txt` в каталоге приложения:

```bash
mkdir -p tmp
touch tmp/restart.txt
```

Проверьте `/api/health` — ожидается JSON `{ "ok": true }`, а затем главную,
оба проекта и `/admin/`. В admin должны сохраниться импортированные значения;
заявка с выбранным согласием должна появиться в секции **Journal** после обновления.
При настроенном боте проверьте также сообщение в Telegram и статус доставки;
при недоступном Telegram заявка должна оставаться в Journal.
Проверьте карту, акцию, цену при 100% оплате, документы и ссылки Домклик.
Без согласия отправка не разрешена. Выход должен закрывать доступ к заявкам.

В инструментах браузера проверьте отсутствие запросов к `workers.dev`,
Cloudflare, GitHub Pages, внешним изображениям и шрифтам. Осознанные переходы
по ссылкам Яндекс/Домклик/мессенджеров сохранены. Реальную доступность и скорость
из российских сетей проверяют после установки: локальные тесты этого не измеряют.

## Если API или admin долго не открываются

Статические страницы может отдавать Apache, даже если Node-приложение ещё не
запустилось. Пустая база с применёнными миграциями возвращает `[]` на
`GET /api/plots`; отсутствие участков само по себе не объясняет зависший запрос.

Сначала проверьте URI приложения в панели Nodejs: для нашей сборки нужен корень
домена, не `/hamper`. Каталог приложения при этом остаётся `hamper`.
Затем проверьте наличие `server.js`, `build/server/start.js`,
`build/server/package.json` и `.env.server` непосредственно в установленной сборке.
`PUBLIC_DIR` для архива — `./public`; `PUBLIC_ORIGIN` содержит только origin,
без пути; `DATABASE_PATH` указывает на существующую приватную базу с миграциями.

Для диагностики включите в панели **«Домены» → «Лог файлы вебсервера»** логирование
нужного домена, затем перезапустите приложение и один раз откройте
`/api/health`. Источники: [логирование Hostland](https://www.hostland.ru/ru/docs/manual/vedenie-logov-i-statistiki-poseshcheniy-webalizer),
[пути Node-приложения](https://www.hostland.ru/ru/docs/manual/avtomaticheskaya-ustanovka-nodejs).

Файл `/home/hostXXXXXXX/passenger_log` находится в корне аккаунта и отличается от
папки `domain_name/logs/`. Ищите свежие сообщения `Unable to start Hamper`,
`Unable to start HTTP server` или успешное `Hamper server listening on …`.
Ошибки запуска завершают процесс с кодом 1, чтобы Passenger не ожидал готовности
уже неработающего приложения. При передаче журнала скрывайте секреты и токены;
содержимое `.env.server` для диагностики отправлять не нужно.

Исправление стартовых файлов загружается поверх `server.js` и
`build/server/start.js`. Оно не требует повторного создания или замены базы,
изменения цен, заявок либо секретов `.env.server`.

## Обновления и резервные копии

Перед обновлением создайте согласованный снимок базы, не копию работающего WAL:

```bash
node --env-file-if-exists=.env.server build/server/cli.js backup /private/path/backups/hamper-before-update.sqlite
```

Команда не перезаписывает существующий файл. Храните несколько копий с разными
именами вне `public/`. Настройте регулярный запуск в Cron Hostland с уникальными
именами файлов и проверяйте создание копий. Резервирование хостера полезно,
но не заменяет проверенный снимок данных приложения.

Для обновления только интерфейса и фотографий используйте
`release/hamper-public-update_YYYY-MM-DD_HH-mm-ss_MSK.zip` (точное имя —
в `release/README.md`):

1. Сохраните резервную копию текущей `public/` вне публичного каталога сайта.
2. Загрузите новую папку `public/` и замените старую целиком, включая `.htaccess`.
   Не объединяйте содержимое: так на сервере остаются старые файлы JS/CSS.
   Если панель поддерживает переименование папок, подготовьте новую рядом и
   переключите её переименованием; иначе выберите время небольшой посещаемости.
3. Проверьте главную, Ойнеловские дали, фотографии, `/admin/` и `/api/health`.
   При проблеме верните сохранённую `public/`. Файлы `UPDATE.md` и manifest
   служат для проверки архива, загружать их в `public/` не нужно.

При таком обновлении `.env.server`, `private/`, база и API остаются на месте;
перезапуск, миграция и импорт данных не требуются.

Для обновления сервера используйте полный
`release/hamper-hostland_YYYY-MM-DD_HH-mm-ss_MSK.zip`:
загружайте новый `public/`, `build/server/`, `server/migrations/` и startup-файл,
сохраняя `.env.server` и каталог данных. Не удаляйте всё приложение вместе с БД.
Затем выполните `migrate`, обновите `tmp/restart.txt` и проверьте health/admin.
Откат кода и восстановление данных — разные операции: для замены базы сначала
остановите приложение, сохраните текущий файл и согласуйте восстановление снимка.

`public/.htaccess` задаёт кеширование и сжатие для статики, которую Apache отдаёт
до Node. Те же свойства реализованы в Node для самостоятельного запуска.
Фактическое применение `.htaccess`, TLS и Passenger проверяется на Hostland;
здесь подготовлен и проверен код, а не действующий серверный аккаунт.
